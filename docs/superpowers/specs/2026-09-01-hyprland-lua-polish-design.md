# Hyprland Lua migration — polish

**Date:** 2026-09-01
**Branch:** `feat/hyprland-lua-config` (PR #186)
**Status:** design approved, awaiting implementation plan

## Context

PR #186 migrated the Hyprland config from hyprlang to Lua (`configType = "lua"`,
Hyprland 0.56.2, home-manager 26.05). The migration landed working:
`hyprctl configerrors` is empty, 91 binds register, config sections apply, and
HDM's `monitors.lua` drives monitors and workspace rules.

This spec covers what the migration left behind — one regression, some stale
references, an unverified startup path — and the Lua-native rewrites the
migration makes possible.

Phase 1 is migration debt and must ship. Phase 2 is optional.

## Phase 1 — correctness

### 1.1 `workspace-manager.sh` monitor resolution (regression)

**Problem.** `resolve_monitor_from_conf` parses `~/.config/hypr/monitors.conf`
with awk (`/^monitor=/`, splitting `$3` on `x` to read the X coordinate) to
decide which physical output is `left` and which is `right`. The migration
changed HDM's destination to `monitors.lua`, so that file no longer exists. The
function falls through to its `WARNING: monitors.conf not found` branch and
queries Hyprland instead.

That fallback is wrong by the script's own documented reasoning: `post_apply_exec`
runs after HDM writes the profile but *before* `hyprctl reload` applies it, so
querying Hyprland returns the pre-reload arrangement. Workspaces can land on the
wrong monitor after a dock/undock. It fails silently and intermittently.

**Fix.** Have the templates state the tag mapping directly, and have the script
read it.

- Each `profiles/*.lua.in` emits a machine-readable header as its first line:
  - docked profiles: `-- hdm: left={{$left.Name}} right={{$right.Name}} laptop={{$laptop.Name}}`
  - undocked profiles: `-- hdm: laptop={{$laptop.Name}}`
- Rename `resolve_monitor_from_conf` → `resolve_monitor_from_profile`; read the
  header with `sed` against `~/.config/hypr/monitors.lua`.
- Keep the existing "file missing → query Hyprland" fallback, and keep its
  warning loud. It is the path that just silently degraded on us.
- Delete the x-coordinate inference awk. The template knows the tag mapping as
  ground truth; inferring it from positions was always a guess.

This is a net correctness improvement over the pre-migration behaviour, not just
a port.

**Why not the alternatives.** Regex-parsing `hl.monitor({...})` lines keeps the
positional guessing and adds Lua-parsing fragility. Reordering to reload-then-move
runs into the hazard the script already documents: `hyprctl reload` can trigger
HDM re-evaluation that kills the script mid-run, so work after reload is
unreliable.

### 1.2 Stale references

- `workspace-manager.sh` comments refer to `monitors.conf` (lines ~86–88, ~100,
  ~136–137) and to `docked-*.conf.in` (WS 9 comment). Both renamed.
- Generated `monitors.lua` runs the template's trailing header comment into the
  following comment on one line, because Go's `{{- … -}}` trims the newline.
  Harmless to Lua (both are `--` comments) but it makes the generated file
  awkward to read while debugging.

### 1.3 Fresh-login verification (gate)

`hl.on("hyprland.start", …)` fires only at compositor startup. Every session so
far began on either the pre-migration hyprlang config or Hyprland's autogenerated
stub, so the exec-once chain has never actually run.

Verify after a real logout/login:

- `noctalia-shell` starts on its own
- `kitty --single-instance --instance-group=hypr` starts
- `theme-toggle restore` applies the saved theme
- `xrdb -merge ~/.Xresources` applies (XWayland scaling)
- fish universal vars and tmux global env carry
  `HYPRLAND_INSTANCE_SIGNATURE` / `WAYLAND_DISPLAY` / `XDG_RUNTIME_DIR`
- `hyprctl configerrors` still empty on a cold start
- a dock/undock cycle puts workspaces on the right monitors (exercises 1.1)

**Phase 2 does not start until this passes.** A cold-start failure could
invalidate assumptions the rewrites build on.

## Phase 2 — Lua-native rewrites (optional)

Ordered: 2.2 first as a low-risk shakedown of the Lua-callback pattern, then 2.1
for the actual payoff.

### 2.1 `zoom-step` → `hl.timer`

Today `zoom-step` eases `cursor:zoom_factor` toward a target at ~60fps from a
detached background subshell: each frame shells out to
`hyprctl keyword cursor:zoom_factor`, then `sleep 0.016`. It coordinates through
a `mkdir` lock and two state files.

A `hl.timer` eases the value in-process. Removes roughly 60 process spawns per
second while zooming, plus the lockdir and both state files.

**Risk.** Timer callbacks run on the compositor event loop under a timeout
budget. The per-frame work is a float update, which is what timers are for, but
a bug here degrades the whole compositor rather than one script. Keep the
callback trivial and bail out cleanly when the target is reached.

### 2.2 `toggle-floating` → Lua bind function

Currently: `hyprctl activewindow -j | jq -r '.floating'`, then one or two
`hyprctl dispatch` calls. As a Lua bind handler it reads `hl.get_window().floating`
and dispatches in-process — no subprocess, no jq, on a latency-sensitive key.

Low risk: `floating` is exposed on the Lua window object.

### 2.3 `window-resize` — blocked, not planned

Branches on the window's `pseudo` state. Lua exposes `pseudo` as a dispatcher
(`hl.dsp.window.pseudo`) and as a window-rule effect, but **not** as a readable
property on the window object — verified against
`src/config/lua/objects/LuaWindow.cpp`. `hyprctl activewindow -j` does expose it.

Working around this (e.g. mirroring pseudo state into a window tag) adds a
correctness burden to save one subprocess on a keypress. Leave it as a script.

### Excluded

- **`monitor.added` event handling.** Lua can react to monitor hotplug natively,
  but HDM already owns this and works, and HDM additionally handles lid and AC
  state via DBus, which Lua cannot reach. Moving half the logic in-process splits
  ownership for no user-visible gain.
- **`hl.notification`, bind handles (`:set_enabled`), query API beyond 2.2.** No
  current need.

## Success criteria

Phase 1:

- Dock/undock places workspaces 1–4 on left, 5–8 on right, 9 per lid state, with
  no `WARNING: monitors.conf not found` in the workspace-manager log
- No references to `monitors.conf` or `*.conf.in` remain outside git history
- Every item in the 1.3 checklist verified on a cold boot
- `hyprctl configerrors` empty after a fresh login

Phase 2 (if taken):

- `zoom-step` spawns no per-frame subprocesses; zoom in/out/reset still eases
  smoothly and no `cursor:zoom_factor` value is left stranded
- `toggle-floating` behaviour is unchanged from the script it replaces
- No new entries in `hyprctl configerrors`

## Notes for implementation

Facts established while debugging the migration, worth not rediscovering:

- The config provider (hyprlang vs Lua) is chosen **once at compositor startup**.
  A live `hyprctl reload` cannot switch it.
- The Lua main chunk **aborts at the first nil call**, so one wrong `hl.*` name
  silently kills the entire config and Hyprland writes an autogenerated stub.
- Reload does `lua_close` + `luaL_newstate`
  (`src/config/lua/ConfigManager.cpp:505`), so `require` caches drop each reload.
  This is what lets `pcall(require, "monitors")` pick up HDM's rewrites.
- Authoritative API names live in
  `src/config/lua/bindings/LuaBindingsConfigRules.cpp:1392` and
  `LuaBindingsToplevel.cpp`. Validate against those rather than documentation.
- HDM skips `post_apply_exec` when a rendered profile is byte-identical to the
  previous one, which is why `undocked-lid-closed` must differ textually from
  `undocked`.
