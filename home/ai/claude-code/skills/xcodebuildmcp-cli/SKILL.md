# XcodeBuildMCP CLI

Use XcodeBuildMCP tools via the `xcodebuildmcp` executable instead of raw `xcodebuild`, `xcrun`, or `simctl`.

> Generated by `xcodebuildmcp@2.7.0 init --skill cli`, then adapted — Step 1 and
> "This Machine" are local. Re-running `init` overwrites both; re-apply them.

## Step 1: Ensure the CLI Exists

Check availability:
```bash
xcodebuildmcp --help
```

Nix provides it (`home/darwin/xcodebuildmcp.nix`, macOS only). **Never
`brew install` or `npm install -g` it** — that shadows the wrapper, which is
the only thing setting the `DEVELOPER_DIR` this machine needs. If the command is
missing, the rebuild hasn't run: `nh darwin switch`.

## Step 2: Use Help-First Discovery

Discover workflows and arguments from the CLI itself:
```bash
xcodebuildmcp --help
xcodebuildmcp tools
xcodebuildmcp <workflow> --help
xcodebuildmcp <workflow> <tool> --help
```

Use this discovery path instead of memorizing static tool lists.

## Step 3: Keep Execution Minimal

- Choose the smallest command sequence that satisfies the request.
- Prefer direct workflow commands over manual multi-step chains unless explicitly requested.
- For simulator run intent, prefer the combined `build-and-run` command.
- Do not chain `build` then `build-and-run` unless explicitly requested.

## Capability Overview

`xcodebuildmcp` supports:
- simulator and device build/test/run
- debugging and log capture
- UI automation
- project discovery and scaffolding
- session defaults and workflow configuration

## This Machine

Verified on Xcode 26.3 / iOS 26.3 simulators. Three things the CLI's own
`--help` won't tell you:

- **One daemon per directory.** The daemon keys its workspace off cwd, so each
  worktree gets its own daemon, its own `.xcodebuildmcp/config.yaml`, and its
  own simulator. Run commands from the worktree you mean; never `cd` elsewhere
  first. `xcodebuildmcp daemon list --json` shows every running workspace.
- **`snapshot-ui` needs Simulator.app frontmost.** Otherwise it fails with
  `No translation object returned for simulator`, which reads like a stale-ref
  problem but isn't. `open -a Simulator` first.
- **The daemon caches env at start.** After any toolchain change, restart it —
  a fresh command alone won't pick the change up.

Expo projects using CNG keep the native `ios` directory as gitignored prebuild
output, so run `expo prebuild` before pointing project-level tools at the
workspace, and expect the generated project to be replaced rather than edited.
